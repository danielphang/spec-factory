## How the seams became sub-tickets

The spec's seams S1–S5 are the skeleton. Four adjustments make every sub-ticket independently mergeable *and* let its acceptance items run at the time it lands; none changes what the spec asks for, only which PR carries which part.

1. **S2's own acceptance needs two commands the spec files under K (S4).** Items 25, 26, 30, 31, 73, 74 call `factory approve-pr` / `factory approve-guardrail`. Those two commands (one approval row each, pushed as the human identity) move into BH-2b. The rest of K stays together in BH-3.
2. **S3's acceptance needs most of K.** Items 35 and 38 call `factory queue`; 37, 48, 49, 81, 83, 84 call `factory resolve`; `build.js` runs "after `factory approve-spec`". So the human surface lands *before* the workflows. The spec says S3 and S4 share `factory/cli.py` and are not parallel; this plan orders K (BH-3) ahead of H (BH-5, BH-6).
3. **S3 is split into three serial PRs**: BH-4 = render + agent definitions (guardrail text a human reads at the PR gate); BH-5 = `intake.js` + the shared `runRole`/clerk/stub machinery; BH-6 = `build.js` + the join. Each is near the spec's ~400-line guide and `build.js` is reviewed with `runRole` already proven by the intake cases.
4. **S2 is split into two serial PRs at hook rule 4** (new in v2, P5). BH-2a is everything about *who may push where* and the store's transport (E, F rules 1–3 and 5, `init`, `install-hook`, commit-and-push of the store); BH-2b is everything about *what may reach `main`* (F rule 4 in `gate.py`, G, L's `gate-run`, K's two approval writers). The two halves are reviewed for different things (credential scoping vs. gate logic, the piece where a bug blocks every merge) and BH-2b can be reverted alone, which is the planner's test for a split. In BH-2a, rule 4 is identity + fast-forward only (rule 1 applied to `main`, marked `# BH-2b replaces`), which is fail-open for the `harness` identity between the two merges; this is safe because no live bare repo exists until `factory init` is run after BH-2b (see Bootstrap), and BH-2a's ⟨bare⟩ items run against the throwaway bare repo its own tests create.

Items that sit under a seam heading but need nothing of that seam are placed where they can run: 59 (wall-clock kill, `run finish` only) → BH-1; 57 (redaction) → BH-2a, where the key it greps for is minted (the redactor is built in BH-1 with an intermediate check); 33 (`--reverts` guard, store-only) → BH-2b as the spec marks it, with BH-1 checking the guard locally; 50 (`resolve --to spec-gate`, `--close`) → BH-3.

**Parallelism: none.** Every candidate pair shares `factory/cli.py`, and a merge forcing an in-flight sibling to re-verify buys nothing on a one-operator Mac. The chain is strictly serial, so `ready-implementers` dispatches one sub-ticket at a time by construction and the parallel-safe exclusion (item 79) is never exercised by this parent itself.

Store IDs: `<parent>.1` BH-1, `.2` BH-2a, `.3` BH-2b, `.4` BH-3, `.5` BH-4, `.6` BH-5, `.7` BH-6, `.8` BH-7.

Conventions every sub-ticket inherits from the parent: all paths relative to `~/dev/nanobot-upstream` on `feat/lionbot-v3`; fixture `pip install -e .`, `AS() { FACTORY_KEY=$1 "${@:2}"; }`, `O` = bare repo URL (BH-2a onward); the gate line (item 67) is `ruff check factory tests/factory && mypy factory && pytest -q tests/factory`; new tests only, under `tests/factory/`; `knowledge_vault/ProjectNotes/SPEC_MAINTENANCE_WORKFLOW.md`, `webui/package-lock.json`, `port_state.json`, `scripts/` are never touched (E9, item 64). Tests that need a bare repo or a store build throwaway ones under a tmp dir via the `FACTORY_STATE` and `FACTORY_REMOTE` overrides BH-1 defines (defaults `~/factory/state`, `~/factory-remote/nanobot.git`); nothing in the test suite touches the operator's live repo.

## Bootstrap: how each sub-ticket lands

Spec v4 §Risk, "Bootstrap": *the seams must land before the gate and `build.js` exist to merge them. Until BH-2 lands, the operator merges with his normal git flow on `feat/lionbot-v3`; after BH-2, `factory init` seeds the bare repo and its `main` is the trunk; BH-3 and BH-4 get their `results record` rows written by hand `AS harness` from a reviewer and a verifier the operator runs himself; from then on item 67 runs on the bare repo's `main` and every later seam merges through `factory merge`.* Applied to this chain:

| Sub-ticket | Merge path | Item 67 runs on |
|---|---|---|
| BH-1, BH-2a, BH-2b | Operator's normal git flow on `feat/lionbot-v3` (PR, own review, fast-forward). No live bare repo exists yet; each PR's test suite builds throwaway ones. **After BH-2b merges, the operator runs `factory init` once**: it seeds `~/factory-remote/nanobot.git` `main` from `feat/lionbot-v3`, creates `tickets`, mints the keys, installs the hook. | `feat/lionbot-v3` |
| BH-3, BH-4, BH-5 | Hand-driven through the gate. The operator creates the parent and sub-ticket records in the store (`factory request new --file plan-build-v2.md`; `factory subticket add` per sub-ticket; `factory ticket set <id> branch=ticket/<id> head=<sha> status=ready-for-checks`), pushes the branch `AS daniel` (rule 1 lets a human push `ticket/*`; rule 2's in-flight check applies only to the `implementer` identity), runs a reviewer and a verifier himself (for BH-3 from the doc's prompt text in a fresh `claude` session; from BH-4 on with `claude -p --agent factory-reviewer` / `--agent factory-verifier` in a checkout of the head, no key in the environment, as item 56 does), and records them: `AS harness factory results record <id> --head <sha> --role reviewer --output r.md` and `… --role verifier --output v.md` (the verifier's `Gate suite:` line writes the `ci` row, L). Every one of these three PRs touches a protected or guardrail path, so `AS daniel factory approve-pr <id> --head <sha>` is required; then `AS harness factory merge <id>`. The hook is authoritative from here: a hand-written row for a stale head is discarded (item 6). | bare repo `main` |
| BH-6 | The pipeline's own path, using the `build.js` in the BH-6 branch: with the sub-ticket in `ready-for-checks` and `head` set, `Workflow({scriptPath: '<BH-6 checkout>/factory/workflows/build.js', args: {ticket}})` runs only the missing checkers (H, resumption: `ready-checkers` lists roles without a row on the current head), real `factory-reviewer`/`factory-verifier` agents in fresh contexts, the join, and `factory merge`. The `approve-pr` row is still the operator's. If the operator prefers not to trust a script that is itself under review, BH-5's hand-driven path is the fallback and the PR says which was used. | bare repo `main` |
| BH-7 | The pipeline's own path with `build.js` on `main`: same as BH-6 but nothing is run from the candidate branch. | bare repo `main` |

Re-plans (item 84's "next free ids") and a later Docker or cron ticket enter the store through the normal intake path once BH-7 is on `main`.
