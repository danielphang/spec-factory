Why one sub-ticket. The change is small: one new command, one new flag, one new input source, two prompt sentences and their documents. I considered splitting it into code (parts A, B and E) and prompts (part C). The split does not make review or rollback easier:
- Both halves edit `docs/design.md`, so they could not run in parallel.
- The parent asks for one changelog entry, 46, that describes the new writers, the roles that receive the log and the question wording together. With a split, either the first half lands design-doc changes with no changelog entry, or the second half rewrites the first half's entry. Either changes what the parent asks for.
- Rollback is by moving the runtime checkout (`~/dev/spec-factory-harness`, the pinned harness revision that runs tickets) back, which a split does not change. The operator's acceptance test of the prompt change (operator step 1) happens before the runtime moves, and does not need a separate merge.
