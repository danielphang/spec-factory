## Problem

The design doc (§Harness table, piece 2, v0 limit (1)) and `specs/build-harness.md` part H route every store read and write through a clerk agent. Spec H gives that clerk a schema shaped like the command's JSON output, so the clerk has to re-type the store's answer into fields. A clerk that re-types it wrongly still passes validation. In the P0 run the clerk invented a field and stringified a nested object, and the workflow script misrouted the ticket without any error. This affects anyone building or running the dispatcher from these documents: every clerk call is a chance for silent misrouting. What the documents should say is that the clerk relays the command's bytes (stdout verbatim, exit code, stderr), the script parses the JSON itself, and a refusal or a reply with no JSON is never read as an answer. The CLI guards stay as they are.

## Root cause

The documents say the clerk's output should be validated by a schema shaped like the command's answer: `specs/build-harness.md` part H (`:268`, restated at `:272`, `:276` and the Risk bullet at `:495`). The design doc's limit (1) doesn't say what the clerk returns. A schema checks only shape, and the clerk has to rebuild that shape by re-typing the data. A wrong rebuild that keeps the shape (an extra field, a JSON string in a slot typed loosely enough) validates, and the script trusts it. Spec B also never states the output format of the clerk's commands, so the documents give the script no reliable bytes to parse.

## Out-of-scope observations

1. Spec H runRole (`:272`) finishes a run with clerk `factory run finish RUN --output-file -` "with `out`". This asks the clerk to pass the role's whole output to the command's stdin, which is the same re-typing hazard on the input side, and STATUS is parsed from that text. The reference harness avoids it: each role writes `runs/<id>/output.md` itself, and `run finish RUN` reads that file. This deserves its own ticket.
2. `plans/build-harness.md` BH-1 lists the CLI surface and BH-5 the intake clerk calls. Neither mentions `ticket show --json` or `factory config` (part C). A plan amendment or re-plan should add them once this spec lands.
3. The script reads `MODELS` from `factory config` but needs a clerk model for that first call. The spec doesn't name a default; the reference uses `haiku`.
4. Spec B says refusals give their reason on stderr (most items), but `factory merge` gives it on stdout (item 21). Part D matches against "the relayed text" (stdout and stderr), so this works, but the inconsistency remains.
