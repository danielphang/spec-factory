Type: bug (design-doc gap in the routing rules, seen in a real P0 run)

Title: A role re-run after a human answers its question does not receive its own prior output (the question it asked)

Summary:
When Triage or the Spec writer parks a ticket with NEEDS-HUMAN and the human answers, the design doc returns the ticket to that role "with the answer" and nothing else. The re-run role never sees the question it asked or the options it offered, so it has to redo the investigation behind them before it can read the answer as an answer. In the P0 run the requester cites, that was a three-option scope question backed by about 3M context tokens of investigation. The requester wants the resolution rule to say a question returns to the asking role with the answer and that role's prior output, and wants the documents to say the same for the Triage and Spec writer NEEDS-HUMAN re-entries. That would make the human-question path match the critic loop, where the re-entering writer already gets its own earlier spec back.

Evidence:
- Request (T-0003): *"Per the table as written, the re-run Triage receives only the request + answer: it does not receive the question it asked, so it must re-derive the three options (and the ~3M context tokens of investigation behind them) before it can read the answer as an answer."*
- Doc text confirmed. `docs/spec-factory.md:76` reads: `A question returns to the role that asked, with the answer; a requester's CLARIFY answer returns to Triage the same way.` In the routing table the `New request → Triage` row receives `The request, ticket search`. No row and no rule gives a re-entering Triage or Spec writer its own earlier output.
- The requester says the critic loop already does this. That checks out in part. The `Critic | REVISE` row gives the writer `Findings, the spec version they apply to`, which is the writer's own earlier output. The `Spec writer | READY-FOR-CRITIC` row gives a round-2+ critic `prior findings … previous spec version`.
- `specs/build-harness.md:311` (`factory resolve --answer`) has the same gap. The answer is "appended to `requests/<ID>.md` under `## Answer <n>`, ticket back to the asking role's ready state", and the role's earlier output is not listed as an input. Item 37 (`:388`) checks only that the re-run's `input.md` "contains the answer".
- Reference harness (read only), `~/dev/nanobot-upstream`, `factory/compose.py` at `0f2e29136`. That is the P0 skeleton commit that created the file, and `git log feat/lionbot-v3 -- factory/compose.py` shows no later change. The triage branch adds the request and then, when the ticket has an earlier finished Triage run, `runs/<last triage run>/output.md` under the heading "Your previous Triage output (the question you asked is answered above)". This confirms the Triage half of the fix is already built. It applies to every Triage re-run, not only ones that follow an answer.
- The reference harness has no as-built fix for the Spec writer half. Its spec_writer branch adds the Triage output, the request, and a previous spec plus critic findings only when `round.spec >= 1 and version >= 1`, along with the human `changes`/`ruling` files. It never adds the writer's own earlier NEEDS-HUMAN output (its open questions).
- Duplicates: none. I checked all seven tickets in `intake/state/tickets/` and their requests. T-0001 (STATUS parser), T-0002 (clerk schema), T-0004 (agents dir), T-0005 (operator steps), T-0006 (P0-5 grep) and T-0007 (single-target harness) all cover other ground. `grep -rn "prior output\|returns to the role"` over `docs specs plans issues prompts` finds only the doc line above and this issue's own source file.

Assumptions:
- A1 (inference): the CLARIFY path is included. `docs/spec-factory.md:76` sends a requester's CLARIFY answer back to Triage "the same way", so if the rule changes, a re-run Triage after CLARIFY also gets its earlier output (its missing-info list). The requester does not mention CLARIFY, but it follows from the rule they want changed.
- A2 (inference): "that role's prior output" means the most recent finished output of that role on that ticket. That is what the reference composer uses for Triage.
- A3 (inference): where the change goes in the documents is an editorial choice, not a product decision. The table has no rows today for a re-entry after a human resolves a park. The requester's "add the same to the Receives column" can be done by amending the resolution rule (Receives "adds to the INPUT the role prompt already declares", `docs/spec-factory.md:68`) or by adding rows. Either way the text must say the same thing in both places.
- A4 (inference, from the request's context and repo conventions, not added scope): a doc change carries a Changelog entry, a matching update to `specs/build-harness.md` (`resolve --answer` at `:311` and the input list for each role's re-entry), and a re-copy of any `prompts/` file whose block changes. Today I expect no prompt block to change, because Receives adds to the role prompt's INPUT rather than replacing it.
- Suggested priority (a suggestion; the human decides): medium. Without the fix each answered question costs a full re-investigation and lets the re-run read the answer against options it rebuilt itself. Nothing is lost or corrupted, though, and the reference harness already covers the Triage half.

Reason: Not needed (ACCEPT). The evidence and the intended behaviour are clear, and no product decision is needed. The requester's wording ("with the answer and that role's prior output") can be used almost as written.

Out-of-scope observations:
- The other resolution paths in the same list may have the same gap. `docs/spec-factory.md:77` returns BLOCKED, critic ESCALATE and planner ESCALATE to the role that emitted them "with the ruling". It does not say whether that role also gets its own earlier output. In the reference composer, a critic re-run at round 1 after an ESCALATE ruling gets the spec and the ruling but not its own escalating findings. The requester did not raise this, so I did not fold it in.
- The reference harness covers only Triage, so it is not evidence that the Spec writer half works in practice. A spec for this ticket should not cite `0f2e29136` as proof for the Spec writer re-entry.
