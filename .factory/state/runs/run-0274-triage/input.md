## Request (raw, with any answers appended)

---
title: "Build worktrees start with no synced environment and an inherited VIRTUAL_ENV; sync once at setup, unset VIRTUAL_ENV in run_env"
labels: "harness"
---
**Problem:** a fresh build worktree has no `.venv`, and role shells inherit `VIRTUAL_ENV` from the launching session's environment. On the Nanobot runner that is blue's `.venv-test`. As a result, `uv run --no-sync` acceptance commands build an empty environment and fail on imports, until the implementer runs `uv sync --all-extras --dev` itself. Every role pays that discovery, and a checker can misread an import failure as a code failure.

**Evidence:**
- Nanobot v3.5 T-0022.1, run-0259 (2026-10-04), reported by the Driver.
- Spec-factory's own runs show the same inherited value: uv warns "`VIRTUAL_ENV=/Users/dphang/dev/nanobot/.venv-test` does not match the project environment path `.venv` and will be ignored" (T-0015 acceptance runs, T-0023 verifiers).

**Proposed change:**
- A. `run_env` (#36) unsets `VIRTUAL_ENV` (and `PYTHONHOME`) for every role command it wraps.
- B. Worktree and checker-checkout setup runs the instance's environment sync once, before the role starts, with `VIRTUAL_ENV` unset. This is a new optional `environment_sync:` command in `instance.yaml`, for example `uv sync --frozen --all-extras --dev`. Without it, behaviour is as today.
- C. The role input says the environment is already synced, so roles do not re-sync.

**Gate:** pre-approved class: it removes repeated discovery work, and no check changes.
