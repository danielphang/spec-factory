This change gives every agent in the spec factory one shared rule: write each section a person reads to a one-page writing standard. The standard is new, at `docs/writing.md`. Two agents that check other agents' work now apply the rule: the spec critic, which reviews specs, and the code reviewer, which reviews code changes. It is for the operator and the other people who read what the agents write. The change builds what its spec describes. The spec was written from a request, and "the request" below means that request.

## What changed

Each agent plays one role, such as planner, triage, critic or reviewer. The change has six parts, A to F.

- **A. The standard.** New `docs/writing.md`, 86 lines. It first says who the reader is: technical, but new to this system. It then lists the sections the rule covers. Then come eight rules, in the order the request gave them. Each rule has one line on how a writer checks it, one Before example with its source, and one After rewrite. Rules 1 to 3 use the operator's three findings from the 2026-10-03 review of the overview draft. Rules 4 to 8 use real outputs from factory runs, each named by its run id: run-0054-planner (twice), run-0052-spec_writer, run-0014-triage and run-0062-verifier. The request named a `checks-in-flight` escalation as an example. An escalation is a problem an agent hands to a human. That one could not be found, as the spec's Evidence section says. Rule 7 uses a real escalation from run-0062-verifier in its place, and names that run. The page ends by naming `README.md` as a worked example.
- **B. How the rule reaches every role.** Every role's system prompt starts with a shared preamble. The preamble's OUTPUT block gains the spec's five lines. Those lines carry the placeholder `{writing standard}`. The block changed in `docs/design.md`, the design document. It was re-copied by hand to `docs/prompts/00-preamble.md` and `factory/prompts/preamble.md`, which remain byte-identical. When a run starts, `fill_preamble` in `factory/instance.py` replaces the placeholder with `str(HARNESS / "docs" / "writing.md")`. The harness is the factory's own code, and `HARNESS` is the harness checkout that is running. The docstring of `fill_preamble` now says this value comes from the checkout, not from `instance.yaml`. As the spec says, it does not refuse to run when the file is missing. Two more edits:
  - The role-context paragraph in `docs/design.md` (line 54) gets both of the spec's additions.
  - The placeholder sentence in `dev/build-harness.spec.md` (line 158) now names `{writing standard}`.
- **C. Critic rubric item 6.** The critic's readability item now covers five spec sections, not only Problem: Problem, Evidence, Open questions, Decisions and Operator steps. In `docs/design.md` the item was replaced with the spec's exact text. It was then re-copied to `docs/prompts/03-spec-critic.md`. The same text went into `factory/prompts/critic.md`. That copy still writes its round limit as the literal `2`.
- **D. Code-reviewer check 8.** A new item 8 follows item 7. It asks whether the operator can read the PR description's What changed and Known gaps sections. A problem there is SHOULD-FIX, never BLOCKING. The item is in `docs/design.md`, `docs/prompts/06-code-reviewer.md` and `factory/prompts/reviewer.md`. The reviewer copy keeps its literal `2`.
- **E. Briefing template.** The briefing is the text every role reads first. Its template, `factory/context.template.md`, gains the spec's four-line bullet. The bullet asks who reads what the roles write. It goes after "What kind of request to expect".
- **F. Records and tests.** `docs/changelog.md` gains entry 43, the next free number. In `README.md`, the sentence "once it exists (#23)" is replaced with the spec's text. A row for `docs/writing.md` is added after `docs/prompts/` in the "Where things live" section. The status header's date was already 2026-10-03, today's date, so it is unchanged. The one test the spec listed changed, and one test file is new. Both are described under "Tests added and changed".

## Tests added and changed

- **Changed:** `tests/factory/test_instance.py::test_system_prompt_is_the_design_preamble_filled_from_the_instance`. This is the one test the spec listed under "Tests to change". Part B adds a third filled line, so the test's comparison of unchanged lines failed as written. The test now finds the index of the `{writing standard}` line. It leaves that line out of the comparison, alongside the first line and the protected-path line. It asserts that the filled line equals the design line with the placeholder replaced by the absolute path of the checkout's `docs/writing.md`. That exact-line check is stricter than checking that the line contains the path. The test also adds `"{writing standard}" not in` to its final check. No assertion was removed or loosened.
- **New:** `tests/factory/test_writing_standard.py`, 5 tests. Each test drives `bin/factory` in a scratch git repo. Like the spec's scenario, each runs `init` and then a triage run on a throwaway store set by `FACTORY_STATE`. So the tests do not need a clean harness checkout. They check three things:
  - The standard file exists and is non-empty, and the run's system prompt holds the line `person reads to the writing standard at <checkout>/docs/writing.md. Those`.
  - No `{writing standard}` is left in the system prompt.
  - Parametrized ×3: the preamble, spec critic and code reviewer design blocks equal their `docs/prompts/` copies byte for byte.
- **Watched failing first.** For this run, the prompt edits were in place, but `fill_preamble` and `docs/writing.md` were not. The new file gave `2 failed, 3 passed`. The two failures were the missing standard file and an unfilled `{writing standard}`. The changed test could not be watched failing on its own assertions. It uses the instance's own store, so from a dirty checkout it is refused earlier, with "harness … has uncommitted changes". It passes in the committed tree.

## Known gaps and uncertainties

- **Agents started as registered role agents do not see the new rule.** Those agents come from the `agents/` templates. The spec's Decisions section requires that this change not touch them, so their copy of the preamble lacks the line. Only runs that read their role from `system-prompt.txt` get the rule. The current intake runs work that way.
- **No agent sees any of this until the operator upgrades the runtime.** The runtime is the harness checkout that runs the agents, at `~/dev/spec-factory-harness`. The operator must move it to a revision that contains this commit and accept that revision. This is the spec's Operator step 1. Until then, the runtime still has the old preamble, and it has no `docs/writing.md`.
- **Untested: whether a live critic blocks on an unglossed term in an Evidence paragraph.** That needs a model run on the upgraded runtime, which is the spec's Operator step 3.
- **Some Before examples in `docs/writing.md` are descriptions or trimmed excerpts, not quotes.** The spec allows this: "short real excerpt or a one-line description". All 3 operator findings are paraphrased. So are the run-0054-planner examples for rules 4 and 8. The overview draft is not in this repo, so findings 1 and 3 are written from the request's account of them. Rules 5, 6 and 7 quote their runs, trimmed with "…" where long. Every After is my own rewrite. Rule 6's After follows the form that run-0015-spec_writer later used for the same item. A reviewer should check that each After is still true to the system. For example, rule 4's After says sub-ticket .6 merged last; line 18 of run-0054's output says so.
- **The page does not say that rule 7's example stands in for the request's.** The request's `checks-in-flight` escalation could not be found, so rule 7 uses one from run-0062-verifier. The page names that source. This note is where the substitution is recorded.
- **The new changelog entry does not follow rule 6.** It starts "After issue #23", an internal reference that rule 6 would ask to be introduced. Entries 41 and 42 use the same style, and I followed the changelog's existing style.
- **The three prompt blocks were re-copied with `sed`, not with `factory render`.** As built, this checkout has no `render` command: `grep -n render factory/cli.py` finds nothing. The `sed` extraction is the same one the prompt-copies-verbatim criterion uses.
