---
title: "Run the spec validator at spec add, not first at the human gate"
---

**Problem, for the gate:** a spec the critic approves can still be refused at the human gate by the harness's own validator, after the whole intake has run. T-0047 (#100), 2026-10-12: critic APPROVE round 1; the operator approved at the gate; `approve-spec` refused with `spec not pinned: scenario '…' has no NEW/REGRESSION label in verification.md` for three scenarios. The labels were present, but two had the scenario name and the arrow on different lines, and all three read `→ REGRESSION in its new form.`, which `LABEL_RE` (`factory/specstore.py:25`) rejects because a word, not punctuation, follows the label. The operator's approval had to be re-done as a format-only gate edit (v2).

**Root cause:** `specstore.validate` and `applies` run only at `approve-spec`, `spec amend` and archive (`factory/cli.py`, the approve-spec, spec amend and archive paths), not at `spec add`. The spec writer and the critic never see the validator's verdict, so a form error reaches the human.

**Proposed change:** run `validate` and `applies` at `spec add` and refuse the version there with the same message, so the spec writer's run fails the way it fails today for other `spec add` refusals and the writer fixes it in its own round. Optionally relax `LABEL_RE` to accept the label followed by a word (`→ REGRESSION in its new form`), or make the spec writer's prompt name the exact form; the spec chooses, and prompts are subject to the replay rule (#80).

**Acceptance the writer can make runnable:** `spec add` with a verification.md whose label line wraps before the arrow is refused with the validator's message and adds no version; a valid spec still adds; `approve-spec` keeps its check.


**Serves (rule B of #116):** operator decisions per change. A form error the harness can find on its own costs a gate decision plus a gate edit (T-0047, v2).
