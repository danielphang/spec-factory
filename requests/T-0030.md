**Problem, for the gate:** most of what a factory run spends on tokens is plumbing, not work. Every role agent re-sends a ~44k-token starting context (Claude Code's own instructions and tool definitions) on every API call, and a separate agent, the clerk, is started just to run one store command and pass its output back. Together these are well over half of all context tokens. The operator pays for it on every ticket; the role prompts and the specs the roles read, which are what we can most easily edit, are a small share.

**Evidence (2026-10-03).** Measured from the surviving Workflow transcripts of both stores (nanobot green's P0 and build pilots, this repo's intake and T-0012): 149 role runs, 741 clerk calls. Context tokens per API call = input + cache read + cache creation, as `factory/cost.py` counts them. A tool result's carried cost = its size (characters ÷ 4) × the API calls after it.

Where the role agents' 247M context tokens went:

| Share | What it is |
|--:|---|
| 47% | Fixed start-up context, re-sent every call. 44.4k tokens for a role run as a general-purpose agent (`inlineRoles: true`), 30.2k for a typed `factory-*` agent with its declared tool list. Of that, ~5k is the instruction files Claude Code loads (`AGENTS.md` 3.4k, memory index 1.3k, global `CLAUDE.md` 0.4k); the rest is Claude Code's own system prompt and tool schemas. |
| 11.5% | The composed `input.md` (spec, findings, plan) |
| 5.8% | Other prose the role opened itself |
| 4.7% | Code read, searches, commands |
| ~30% | Unattributed; mostly the characters ÷ 4 estimate undercounting code |

By role, `input.md` is 4% (triage) to 23% (reviewer) of a run. Spec Evidence is the largest input section (14–16 KB per spec), and a round-2 critic receives both full spec versions.

The clerk: 741 calls, 46.9M context tokens (about 16% on top of all role spend), each call two API calls at ~30k tokens, to run one `bin/factory` command. This is the measurement #15 started from (83 of 94 agent calls in a stubbed two-sub-ticket build); #15 was closed with "reopen if the dispatcher itself is the cost", and it is.

Which runs were typed: 21 of 118 role runs. The rest ran inline, because the session that started them predated `.claude/agents/` (green, P0) or the instance has no agent files (this repo, `.factory/README.md` "Running").

**Proposed change**, three parts, largest saving first:

A. **Typed role agents everywhere.** Every role runs as its `factory-*` agent with only its declared tools; `inlineRoles` becomes a fallback that logs a warning in the run's `meta.yaml`. This repo's instance gets its agent files (via `factory init`, which already copies them). Expected: starting context 44.4k → 30.2k per call, about 15% of role spend.

B. **No clerk agent.** The dispatcher runs `bin/factory` itself and reads its JSON directly. Options for the planner to choose between: a Python driver (`factory drive TICKET`) that runs roles as `claude -p --agent factory-<role>` and owns routing; or keeping the Workflow scripts if a shell primitive is available to them. The routing table, round limits and refusals stay in the CLI either way. Expected: the 46.9M clerk tokens, about 16% on top of role spend, and the clerk's failure modes (re-encoded JSON, #2).

C. **Role-specific inputs.** `compose.py` sends each role only the spec sections it uses: planner, implementer, reviewer and verifier get Problem, Proposed change, Acceptance, Risk, Tests to change and Out of scope, not Evidence or Responses. A round-2 critic receives the diff between spec versions instead of both. Expected: roughly a third of the 11.5% input share.

**Decisions:** saving tokens never removes a check: every role keeps reading the code it judges, and no role loses an input its prompt names as required. The spec text itself (what writers put in Evidence) is #23's, under "agents are readers too": pointers by file and function name rather than line ranges, measured output only when it is costly to reproduce.

**Acceptance the writer can make runnable:** re-run the measurement on one real ticket after each part lands and record the per-role starting context, the clerk share, and the `input.md` share beside the figures above. Add the measurement to `factory/cost.py` (`--breakdown`) so the retro and later tickets can repeat it.

**Out of scope:** model choice per role, effort per role (#22), Claude Code's own system prompt.

**Risk:** part B rewrites the dispatcher; the workflow scripts are protected (`harness` class) and the routing must not change. Part A touches `agents/` and each instance's `.claude/agents/`. Sequence A and C first (small, independent); B after them, with the before/after measurement.

**Comment on the issue:**

Operator constraint (2026-10-03), recorded by the Green session: **the dispatcher stays the Workflow tool.** Part B's Python/Agent SDK driver is ruled out, for two reasons.

- **Progress view.** The operator follows runs in the Claude mobile app. Workflow runs show there, and a separate SDK driver would not.
- **Billing.** The Agent SDK docs direct API-key authentication: "Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK" (code.claude.com/docs/en/agent-sdk/quickstart.md). Moving to the SDK would move the factory off the operator's subscription onto API billing.

What this leaves for part B: cut the clerk inside the Workflow tool by batching the bookkeeping. One clerk call per role run instead of four or five, through a single CLI step that does run start + compose before the role and run finish + results record + transition after it. In this session's runs 991 of 1,143 agent starts (87%) were clerk calls. Parts A (typed agents) and C (role-specific inputs) are unaffected.

**Comment on the issue:**

Wall-clock data from the first full run on the new layout, T-0013 (#23): 15 files, +270/-47, one sub-ticket.

- **Build: 27.5 min** from approval to close. Planner 2.0 min; implementer 9.5; reviewer and verifier in parallel, about 6.5; merge; parent-close verifier 5.5. Clerk relay: 38 clerk calls against 5 role runs, about 4 min at roughly 6 s each.
- **Intake: about 23 min** of machine time from the triage answer to the gate. The spec writer took 14.1 min, the critic 6.3.

Two cuts in scope here:
1. **Parent-close verify on a one-sub-ticket parent repeats the sub-ticket's verify.** T-0013.1's verifier VERIFIED at 18:28. The parent verifier then re-ran the same scenarios and the same 116-test gate on the merge of that head into an unchanged main, and VERIFIED at 18:35. When a parent has exactly one sub-ticket, main has not moved since its checked head, and the sub-ticket's acceptance list contains every parent scenario, the parent close could reuse the sub-ticket's VERIFIED row. That saves about 5.5 min, 20% of this build. Needs: a planner rule that a lone sub-ticket carries the parent's full acceptance, and a join/close rule in the CLI.
2. **The clerk**, as above: about 15% of build wall time here, through batching.

**Comment on the issue:**

Operator decision (2026-10-03): **part B (no clerk agent) is deferred; the clerk stays on Haiku.** Possibly a nothing burger on a subscription. Why, from a follow-up costing of the same sample:

- **Priced at API list rates** (input side measured exactly, output a floor from visible text since transcripts undercount output): the whole sample is ≥ ~$175. The clerk is ≈ $19 of it (~11%), about 2.5¢ per call, almost all of it Haiku cache writes. The role agents are the rest, and the Opus/Fable cache writes and thinking output dominate them.
- **On a subscription, tokens are not the bill.** Anthropic documents no per-model weighting and nothing about cache reads, but the two official data points (weekly-limit hours per model in Aug 2025; at the Opus 4.5 launch, Opus caps removed with "roughly the same number of Opus tokens as you previously had with Sonnet" after a price cut) suggest usage tracks something close to API price. The factory burned ~294M context tokens over three days, ~80% cache reads, and hit one session limit, so cache reads cannot count at face value. If that holds, the clerk's ~16% share of tokens shrinks to roughly its ~11% share of dollars, at Haiku prices.
- **Cost of the fix vs the saving.** B rewrites the dispatcher for about a tenth of the spend. A (typed agents, ≈ 9%) and C (role-specific inputs, ≈ 3%) are small changes and stay in scope.

**Acceptance addition:** record `/usage` (session and weekly bars, with the subagent breakdown) before and after the measured run, beside the token and dollar figures. That is the only real measure of what the factory takes from the plan. Revisit B only if `/usage` shows the clerk's share is materially larger than ~11%.

**Comment on the issue:**

From the Nanobot v3.5 Driver (2026-10-04), confirmed on the runtime: `agents/` ships definitions only for the intake roles and the clerk (clerk, planner, spec-critic, spec-writer, stub, triage). There is none for the implementer, reviewer or verifier. So `build.js` without `inlineRoles` fails at the first implementer call ("agent type 'factory-implementer' not found", workflow wf_345169c6-fca). Part A (typed agents everywhere) must therefore include:
- agent files for the three build roles, with tool fences: the reviewer and verifier must not edit the worktree;
- `init` copying them.

Until then, the build half runs only with `inlineRoles: true`, so the reviewer and verifier run without their fences. Both instances do this today.

A second defect in the same run, for the harness: when an agent call fails, the build workflow left the sub-ticket holding an orphan in-flight run and returned without parking. Any agent() failure in a role call should record the run KILLED and park with the error. That belongs with #33's silent-exit fix.

**Operator scope and gate (2026-10-04):** "i really want the efficiency stuff done". Scope is #24 **parts A and C only**. Part B (no clerk / batching) stays deferred by the operator. Fold in #22: an optional per-role `effort:` map beside `models:`, passed to each role's agent call and recorded in the run's `meta.yaml`. The spec gate is pre-approved.
Constraints to honour:
- **A must create agent definitions for all seven roles**, including implementer, reviewer and verifier, which `agents/` lacks today (the Driver hit "agent type 'factory-implementer' not found"). The checkers (reviewer, verifier) get tool limits: no edits to the worktree under review, only their run's scratch and output.
- `init` copies them.
- `inlineRoles` stays as a supported fallback.
- Session restarts are operator steps: the runner sessions for spec-factory and Nanobot must restart to register agents. The spec says what happens if a workflow runs without inlineRoles before the restart.
- **C** trims each role's input to the sections it uses. Measure the before and after input size per role, from the store's `input.md` files.
