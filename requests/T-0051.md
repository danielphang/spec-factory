# Get one harness-suite run well under the 10-minute tool-call cap, so roles stop backgrounding it (spec-factory #106)

**Where:** the harness suite (`tests/factory`, 576 tests) and the gate commands that run it (`.factory/config`, the verifier's REGRESSION checks).

**Problem:** one full suite run now takes 7–10 minutes, and a single tool call is capped at 10 minutes. Under load, or when a role runs two suites at once, it crosses the cap. The role then starts the suite in the background and ends its turn waiting for it, which is #41's failure again: no output, `EMPTY-OUTPUT`, a redispatch of the same role, and the same result.

**Evidence:**
- T-0047.2 (#100) parked 2026-10-12 20:29Z, `EMPTY-OUTPUT from verifier`. Both run-0486 and run-0487 ended with "Waiting for the suite runs to finish before writing the output." The reviewer gave APPROVE on the same head. The implementer (run-0484) wrote: "One full suite run takes about 9 to 10 minutes on this machine, close to the 10-minute limit a single tool call allows. I had to run it in the background."
- Measured suite times: 443.67 s on a quiet scratch clone at `700ce73` (Green, 2026-10-12). Verifier runs: 479 s and 525 s (run-0476), 552–563 s (run-0483), 556–561 s (run-0473), 605 s (run-0471, run alongside a second suite).
- No small set of tests dominates. The 40 slowest take 151 s of the 443 s, with the top one at 19 s (`test_shepherd.py::test_a_sibling_refused_three_times_and_fixed_each_time_still_merges`). The other 536 tests average about 0.55 s each, which is mostly spawning the CLI as a subprocess (`tests/factory/_cli.py`, `_fixtures.py`).
- The preamble already says to run every command in the foreground (`factory/prompts/preamble.md:45`, from #41). A role can't follow that rule when the command takes longer than the tool allows.

**Proposed change (harness, no prompt change):**
- A. Get one suite run well under the cap, with a target under 3 minutes. The candidates:
  - run in parallel with `pytest-xdist` (`-n auto`), a dev dependency added through uv, after checking the tests don't share state;
  - call the CLI in-process in `_cli.py` instead of spawning a subprocess each time.
  
  Measure both and pick by speed. Keep the load-sensitive timing test (`test_drive_build.py::test_build_step_lines_and_the_status_file_name_the_subticket_in_flight`, flaky 2 runs in 4 under load in run-0484) passing under parallel runs.
- B. Gate commands and the verifier's suite REGRESSION use the faster form.
- C. When an `EMPTY-OUTPUT` role's last message says it is waiting on a command, the park reason says so ("ended its turn waiting on a background command"). A blind redispatch then doesn't repeat it.

**Not in scope:** a preamble change. That's a prompt change and needs the golden baseline first (#96 row 4a).

**Order:** after T-0047 (#100) finishes, since that ticket is moving `factory/cli.py`. Until then, a redispatch on a quiet machine fits under the cap.
