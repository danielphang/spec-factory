# Workflow builds park on the clerk's relays: write each role's model into the script at launch, and parse a reformatted reply (spec-factory #109, #112)

**What is wrong:** the Workflow scripts (`factory/workflows/build.js`, `intake.js`) learn everything through the clerk, a cheap model that runs one CLI command and relays its stdout. The clerk changes what it relays in two ways, and each costs a park and a human to resume:

- **It changes a value (#109).** Relaying `factory config`, it retyped the verifier's model from `opus` to `fable` in 5 of 8 builds on 2026-10-12 and 2026-10-13. Every hit was the same change. Since #107 (T-0050), `run start` refuses the wrong model, so nothing runs on it, but the sub-ticket parks (`harness-bug: run start verifier: model fable refused…`). T-0052.1 parked three times this way and was finished only by `factory drive`, which reads the config in Python.
- **It reformats (#112).** On 2026-10-14, on the Nanobot target, the clerk returned `factory run finish`'s one-line JSON pretty-printed over many lines. `clerk()` (`build.js:46-52`) parses only single lines from the end, found none, and parked a sub-ticket whose implementer had finished READY-FOR-REVIEW, before `ticket head`. No `resolve` route covers that park; it was resumed with `ticket head` plus a raw `ticket transition --to checks-in-flight --round pr:init`, then a relaunch, which merged it.

**Evidence:** #109's body (clerk transcripts: the Bash result said `"verifier": "opus"`, the StructuredOutput said `"fable"`, every other byte the same) and #112's body and comment. `common.out()` prints `json.dumps` with no indent, so every pretty-printed reply is the clerk's doing.

**Why retrying is not the fix:** #109 first proposed a digest of the models and a re-read on mismatch, up to 3 times. The error is a steady bias, not noise: at 5 in 8, four tries still all fail about 13% of the time, and T-0052's two builds both failed, so retries may not be independent.

**Requirements from the operator:**
- **A. Each role's model reaches the script without a model relaying it.** At launch, the harness writes a copy of the workflow script with the instance's models (and the other values the script now reads from `factory config`) filled in as a literal, and the operator or session launches that copy. The script then takes no model from a clerk reply. Writing the copy at every launch keeps it in step with the instance's config; the copy records the harness revision and instance it was written for. Writing it runs the same harness-acceptance check `factory config` runs, and refuses where `config` would. Where the copy is written, and the command's name, are the spec's call; it must not be the live store, and it must not need a commit.
- **B. A reformatted reply still parses.** `clerk()` in both scripts tries `JSON.parse` on the whole trimmed stdout before the current last-line scan. Whitespace reformatting then loses nothing; a changed value is still caught by #107's guard at `run start`.
- **C. A route back from #112's park.** A sub-ticket parked from ready-for-implementer whose last implementer run finished READY-FOR-REVIEW can be resumed with `resolve`: it reads the branch tip (`ticket head`) and moves to checks-in-flight, round unchanged, as the script would have. Its name and flag are the spec's call.
- **D. Tests:** running the script under node with stand-in `agent()` calls (T-0050's verifier did this by hand; the suite has no such test yet) shows a launch copy runs every role on the instance's model with a clerk that retypes models; a fixture with a pretty-printed clerk reply proceeds; the resolve route is refused for any other park.
- README's how-to for launching a workflow says how to launch the copy, and a changelog entry.

**Must not change:** `run start`'s model refusal from #107 stays as the backstop. `factory drive` is untouched. The clerk stays for every other relay; #89 retires it.

**Decisions taken:** writing the models into the launch copy rather than a digest and re-read (above). Rejected: the launching session passing the models in the Workflow's `args`, because that session would type them, so it is not deterministic; relaying the config encoded so the clerk cannot read it, because it is still copied by a model.

**Risk the spec must address:** Claude Code's auto-mode classifier once refused a session's one-off edited copy of `build.js` as a guard bypass. This change is reviewed harness code that keeps the guard, but the spec should say how the launch copy is told apart from an edited script (for example, it is written only by the harness command, at a path it owns, with the harness revision in it).
